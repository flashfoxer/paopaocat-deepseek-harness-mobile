# 手机版「在线更新」方案（2026-10-13 讨论稿）

## 0. 一句话

**检查更新 + 应用内下载 + 交给系统安装**：分三步做，先做"提示"（1 天），
再做"应用内下载并安装"（1-2 天），最后做**包瘦身**（2-3 天）—— 第三步才是
"更新不痛"的关键（现在 111.5 MB 一次全量下载，手机上很痛）。

---

## 1. 先说清楚 Android 的现实约束（避免不切实际的期待）

| 约束 | 事实 | 我们的对策 |
|---|---|---|
| **不能静默安装** | Android 8+ 起，普通 App **不能**自己装 APK；必须弹系统安装界面，用户点确认 | 不承诺"自动安装"；我们是"下载好、点一下装" |
| **要用户授权** | 需要 `REQUEST_INSTALL_PACKAGES` + 用户在系统里允许"来自此来源的安装" | 权限**已声明**；未授权时引导到设置页并写清路径 |
| **签名必须一致** | 覆盖安装要求新旧包**同一签名**；换了签名就必须卸载重装（数据丢） | 我们 v0.14→v0.74 一直是同一把调试证书 ✓ **但换正式证书要趁早**（见 §7） |
| **没有应用商店** | 我们走 GitHub Release 侧载 → 商店自带的更新机制用不上 | 自己做更新链路 |
| **GitHub 网络不稳** | 国内访问时好时坏 | 超时 5 s **静默失败**、不弹窗骚扰；支持用户自填镜像地址 |

## 2. 手上已经有什么（可直接复用，不用造轮子）

| 需要的能力 | 已有的东西 | 状态 |
|---|---|---|
| 下载（多源测速 + **断点续传** + **sha256 校验** + 原子落盘） | `app/lib/local/model_downloader.dart`（为 1-3 GB 模型写的） | ✅ 直接复用 |
| 安装权限 | `AndroidManifest.xml` 已声明 `REQUEST_INSTALL_PACKAGES` | ✅ 已就绪 |
| 把文件交给系统 | `MainActivity.openFileByPath()`（FileProvider + `ACTION_VIEW`） | ✅ 加一个 `setDataAndType(package-archive)` 分支即可 |
| FileProvider 白名单 | `res/xml/file_paths.xml`（严格白名单，逐条有用途注释） | 加一条 `updates/` 即可 |
| 版本号 | `app/lib/app_version.dart` 的 `kAppVersion` | ✅ 已就绪 |
| 更新说明 UI | `release_notes_page.dart`（按版本展开） | ✅ 可承接"新版有什么" |

## 3. 三层方案（按"先能提示 → 再能装 → 再变小"排）

### L1 检查 + 提示（1 天，**建议先做**）—— ✅ **已实现（2026-10-13，0.75）**

- **更新源**：仓库根目录一个 `update.json`
  （走 `raw.githubusercontent.com`，比 GitHub API 稳、不限速；API 作兜底）
- **查询时机**：① 设置里「检查更新」手动查；② App 启动后**异步查一次**
  （可关、超时 5 s、失败**静默**只写日志）
- **有新版**：设置页顶部一张卡片 —— 「**0.75 可用** · 111.5 MB · 3 条修复」+「看更新说明」+「下载」
- **数据结构**（同时是给更新源的文件格式）：

```json
{
  "version": "0.75",
  "versionCode": 75,
  "url": "https://github.com/zmm863-commits/paopaocat-deepseek-harness-mobile/releases/download/v0.75/paopaocat-preview-0.75-arm64-v8a.apk",
  "size": 111504031,
  "sha256": "……",
  "minVersionCode": 0,
  "publishedAt": "2026-10-14",
  "notes": ["修好 ……", "新增 ……"]
}
```

- 版本比较：先比 `version` 的数字段（`kAppVersion` 够用）；要更严就从 Android 侧把
  `versionCode` 带过来比对。

### L2 应用内下载 + 交给系统安装（1-2 天）—— ✅ **已实现（2026-10-13，0.75，与 L1 同版）**

> 实现与计划的三处偏离（都是实现时才发现更该这么做的）：
> 1. **没有复用模型下载器**，而是新写了 `local/apk_downloader.dart`：
>    模型那边要吃 `OnDeviceModel` 条目 + 多源测速，更新包只有一个直链，硬套只会把两边搞脏。
>    但**三条底线与它完全一致**，且 `sha256OfFile` 直接复用同一份实现。
> 2. **多了一条"文件名洗净"**（`sanitizeApkFileName`）与**体积上限 2 GB**：
>    文件名是从清单里的 url 推出来的 —— 那是**网络给的东西**，不洗就可能路径穿越。
> 3. **下完立刻验签名**（不等用户点安装才验），把"这个包不是同一家签的"提前摆出来。
>
> 验证：`flutter analyze` 零问题；全量测试 891+ 通过 / 0 失败；
> 下载器 13 条本地假服务测试（含"服务器不认 Range"与"哈希不符必须删包"）。

1. 复用模型下载器 → 存到 `files/updates/paopaocat-preview-X.Y-arm64-v8a.apk`
2. **安装前两道校验（安全底线，缺一不可）**：
   - **sha256** 与源里给的一致（也可与 GitHub Release 资产自带的 `digest` 交叉验证 ——
     实测过它给的 sha256 是精确的）
   - **APK 的签名证书与当前已装应用一致**（`PackageManager.getPackageArchiveInfo(...,
     GET_SIGNING_CERTIFICATES)` 比对）—— **不一致就拒绝安装**，这是防止"更新被换成恶意包"
     的关键一步
3. 安装：`ACTION_VIEW` + `setDataAndType(uri, "application/vnd.android.package-archive")`
   + `FLAG_GRANT_READ_URI_PERMISSION`；先 `canRequestPackageInstalls()`，
   未授权则引导到系统「安装未知应用」页
4. UI 如实：进度、校验结果、失败原因都写清楚；**下载完不自动装**，等用户点「安装」
5. （可选升级：改用 `PackageInstaller` 会话 API —— 系统级进度、更规范，但复杂一些，先不做）

### L3 包瘦身：让"更新"这件事本身变小（2-3 天，**价值最大**）

现在 111.5 MB 全量下载 = 每次修复都在赌用户的流量和耐心。把**大块外置**：

| 现在随包的大块 | 大小 | 改法 |
|---|---|---|
| `dsh-runtime.zip`（DSH 运行时） | 33.7 MB | 首次启动按需下载（已有断点续传/校验） |
| sherpa-onnx + ffmpeg 等 `.so` | 25.9 MB | 保持随包（要能离线用语音），或按"是否用语音"拆分 |
| 中文语音模型 | 31.5 MB | **已经**是按需下载 ✓ |

目标：APK 本体降到 **~40–50 MB**，之后每次修复的下载量**减半以上**。

> **差量包（bsdiff / HDiffPatch）先不做**：要构建端流水线 + 客户端合并 + 失败回退，
> 复杂度高，而收益大部分被 L3 覆盖。

## 4. 更新源与网络

> ⚠️ **2026-10-13 实测后改过口径**（原文写的是"主源 raw、兜底 GitHub API"，
> 实测发现真实差别在**缓存新鲜度**而不是速度，故定案如下）。

### 两个东西放两个地方（这是这套方案唯一的"工程点"）

| 放什么 | 放哪里 | 为什么 |
|---|---|---|
| **版本清单** `update.json`（1 KB 量级） | **Git 仓库根目录**（与 `README.md` 并排）；`git push` 完就有公网地址 | 纯静态文件、不消耗 API 配额、能自定义字段（`minVersionCode` / `notes` / 镜像） |
| **APK 本体**（110 MB 量级） | **GitHub Release 附件**（**不进仓库**） | ① GitHub 单文件硬限 **100 MB**，111 MB 的包会被直接拒绝推送；② jsDelivr 对 GitHub 单文件另有 **20 MB** 上限；③ jsDelivr **不能代发 Release 附件**（实测 404） |

### 两条清单源，主次是这么定的（本机实测，2026-10-13）

| 源 | 1 KB 小文件实测 | 缓存响应头 | 结论 |
|---|---|---|---|
| `raw.githubusercontent.com/<repo>/main/update.json` | **0.47 s** | 几分钟 | **主源**（快且新鲜） |
| `cdn.jsdelivr.net/gh/<repo>@main/update.json` | 2.16 s | `s-maxage=43200` · `x-jsd-version-type: branch` = **12 小时** | **只当兜底** |
| `api.github.com/repos/<repo>/releases/latest` | 2.10 s · 7.5 KB | — | 可选（自带 tag/直链/`sha256` digest），匿名 **60 次/小时/IP** 限流，故不进主流程 |
| Release 附件直链 | HTTP 206 · 2.27 s | — | **包本体走这条，支持断点续传** |

- **为什么不是 jsDelivr 当主源**：它对"分支"的缓存是 **12 小时** —— 推了新清单后，
  走 CDN 的用户最多半天才看到新版，而更新检查最怕"发了新版没人看得见"。
  真要立刻生效可以调 `https://purge.jsdelivr.net/gh/<repo>@main/update.json` 清缓存
  （实测可用，`status: finished`），但那是发版时多一步人工操作。
- ❌ **一条被推翻的旧实测**：曾记过"raw 慢到 25 秒超时"——那是 **26 KB 的 README**
  撞上网络抖动，不是 raw 对小文件的通病。小文件实测 raw 反而更快。留此更正，免得再翻案。
- **失败必须静默**：三条源依次回退，全不通时**不弹窗、不卡启动**，只写日志，
  设置页里如实说"这次没查到"并给出每一步卡在哪。
- **用户可自填镜像**：设置里允许覆盖（国内网络的自救手段）；填了就用它，不再试内置的。

### 清单格式（`update.json`，也是给更新源的契约）

```json
{
  "version": "0.74",
  "versionCode": 74,
  "url": "https://github.com/<repo>/releases/download/v0.74/paopaocat-preview-0.74-arm64-v8a.apk",
  "size": 111504031,
  "sha256": "……",
  "minVersionCode": 0,
  "publishedAt": "2026-10-13",
  "notes": ["修好 ……", "新增 ……"]
}
```

只有 `version` 与 `url` 是**必需**的；`size`/`sha256` 缺了只是不能精确显示与校验。
解析是**严进**的：缺必需字段就报错并**点名是哪个字段**，绝不返回"半个对象"
（半个对象会变成界面上的"0.00 可用"）。

## 5. 灰度与强制更新（慎用）

- `minVersionCode`：只有**真正不兼容**才设成必须更新
- **必须留"仍要继续"出口** —— 否则网络不通的用户会被永久锁死在门外
- 不需要复杂灰度：`update.json` 手改即可

## 6. 工作量与实施顺序

| 阶段 | 内容 | 工作量 | 何时做 |
|---|---|---|---|
| L1 | 检查更新 + 卡片 + 更新说明（从 JSON 读） | **1 天** | 下一版就能带上 |
| L2 | 应用内下载 + 双校验 + 系统安装 | 1-2 天 | 紧随 L1 |
| L3 | 大块外置、APK 瘦身到 ~40-50 MB | 2-3 天 + 真机验证 | **优先级其实最高**（体验收益最大） |
| 之后 | 差量包、PackageInstaller 会话、多渠道 | 按需要 | — |

## 7. 要提前定的两件事（越早越省事）

1. **签名要不要换成正式证书？**
   现在全系列用调试证书（`7aaf4448…d3cc17`），好处是覆盖安装一路顺。
   一旦以后换正式签名密钥，**老用户必须卸载重装（数据会丢）** ——
   所以这个决定**越早做越好**，最好在自动更新铺开之前定下来。
2. **要不要上应用商店？**
   上架就有商店自带的更新机制（省掉 L2），代价是包体审核、合规材料、
   以及国内商店各家的要求。若打算上架，L1/L2 仍值得做（未上架期间的用户）。

## 8. 一个"零开发"的旁路（供参考）

第三方更新器（例如能跟踪 GitHub Releases 的 Obtainium 这类）可以让**技术型用户**
自己完成"检查 + 下载 + 安装"，我们一行代码都不用写。
但它替代不了 App 内更新：普通用户不会装第二个 App 来给自己更新。
