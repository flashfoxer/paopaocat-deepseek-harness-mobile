# 「免费大模型」方案（2026-10-13）

## 0. 一句话

**单条通道的伪装路线已经死了**（上游把匿名免费层关了，实测补齐全部已知契约仍 403）。
出路是把它改成 **「多家免费额度 + 自动故障转移」** —— 正大光明用各家公开的免费额度，
一家限流/失效就自动换下一家，界面如实显示每家状态。

---

## 1. 当时复刻的是什么（留个准确记录）

**`FishBottle7/opencode2dsh`** —— 用户 2026-10-11 给的，并定调「仍想要 OpenCode 这条通道，
**设置里显式开启的实验性通道**」。

`app/assets/toolbox/zen-proxy.mjs` 就是照它的实测记录实现的：

- 上游自 2026-09-16 起对非官方会话形状返回 `403 FreeTierError`；
- 它记录的当时门禁只查两件事：① `x-opencode-session` 是 `ses_` + 12 位小写 hex + 14 位 Base62 的**形状**；
  ② 请求体 `stream: true` 且 `tools` 里有名为 **`bash`** 与 **`read`** 的函数工具。
- 它另带一个**可选的 IP 池**（设置页里的 `multi-exit rotation`）来分摊**按出口 IP 的配额** ——

  （它的取舍）。我们没做重试、选择**如实报错**：更透明，但体验略差 ——
  **这一条我可以补成「小步退避 + 换源」**。

## 2. 现在的实测结论（2026-10-13，本机直连）

| 请求 | 结果 |
|---|---|
| `stream:false` + 只有 `read` | 403 FreeTierError |
| **`stream:true` + `bash` + `read`（完全照门禁记录）** | **403 FreeTierError** |
| `stream:true` + 无 `tools` | 403 FreeTierError |

三行都带齐了 CLI 伪装头（UA `opencode/1.18.31`、`x-opencode-client: cli`、`x-opencode-project`、
形状正确的 `x-opencode-session`）。**结论：门禁已不在请求里。**

旁证两条：① 社区插件 `viztor/dsh-opencode-patch` 的 README 自己写着「the gate is not in the request, measured」，
并说要用**一个凭据**（登录或 Zen/Go Key）才稳；② 2026-08-27 那次排查已实测 **OpenCode Zen 对大陆 IP
本身就是地区封锁**（`403 RegionError`）。所以这条路对国内网络**本来就不稳**。

用户手机上的原话（v0.73 报告）：`[zen-proxy] 上游 HTTP 403：FreeTierError: ...` —— App 的报错文案是对的
（如实说"上游拒绝了、可能又收紧了"，并给"等它恢复 / 先关掉换别的模型"两条路）。

## 2.1 最新解法（2026-10-13 实测通过，通道可以救活）

**先说结论：这条路今天能修，而且我们已经修好并实测通过了。**

排查链路（每一步都有取证）：

1. `opencode2dsh` 的最新版是 **v0.3.11（10-11）**，它解决的是 **10-10 那次**变动
   （通道搬到 `/inference`、要求 `bash`/`read` 工具、`Bearer public` 会被 401）——**不是今天这次** ✗；
2. 它自己的 issue **#62（10-13 当天新开）** 里，用户报的故障和我们一模一样（"API 密钥无效"/403
   `FreeTierError`），有人指向跨项目的同源故障 **`decolua/9router#4780`**；
3. 那份 issue 把真因写清了：**上游开始校验会话 id 的前 12 位 hex 能不能解码成合理的时间戳**
   （真客户端编码 `~(BigInt(Date.now()) * 0x1000n + counter)` 取低 48 位）。各家复刻实现
   （含我们）都是把种子 **sha256 派生**出这 12 位 ✗ → 一律被判成"不是 OpenCode 客户端" → 403。
   形状早就对了，**语义**不对。

**本机复核（不是照抄）**：curl/HTTP2 + 今天在售的免费模型（`big-pickle`）+ 旧的摘要派生 id → 403；
换成时间戳编码的 id → **200 且真流式吐字**。`Authorization: Bearer public` 可带可不带；
`tools` 里的 `bash`+`read` 仍然必需（缺了 403）。

**改动**：`canonicalSessionId()` 里那 12 位改为时间戳编码（基准按天取整 → 同一天内同一会话
拿到同一个 id，保住 prompt-cache 亲和；上游不校验会话新旧，实测 30 天前的照样 200）。

**验证（对真正出货的产物做的端到端）**：

| 项 | 结果 |
|---|---|
| 补过之后的代理，端到端发一次对话 | **HTTP 200**，10,824 / 10,273 字节真 SSE，模型真回了内容 |
| 同一 seed 两次 | **完全相同的会话 id** ✓（缓存亲和没丢） |
| 不同 seed | 不同的会话 id ✓ |
| 形状 | 全部匹配 `ses_` + 12 位 hex + 14 位 Base62 ✓ |
| 用本地回声服务器抓真实外发请求 | `Bearer public` + `tools=[bash,read]` + 时间戳 id ✓ |

**⚠️ 但请把它当"临时救活"，不是"修好了"**：这是 4 天内**第 4 次**上游变动
（09-17、10-09/10-10、10-11、10-13）。每一次都得重新逆向 + 改代码 + 重发包。
所以 §3 的多源方案**仍然要做** —— 它的价值恰恰是"不用跟着单条通道的变脸跑"。

## 2.2 第 5 次变动（2026-10-13/14）与我们的修复（2026-10-15）

**先说一句**：§2.1 那次（10-13 的时间戳会话 id）**当时确实修好了** —— 实测 200 + 真流式吐字。
但那份文档自己也写着"**把它当临时救活，不是修好了**：这是 4 天内第 4 次变动"。
现在就是**第 5 次**。

**这次换了四处（社区用自签 CA 中间人抓官方 1.19.0 客户端的真实请求 + 逐字节重放测出来的）**

| 项目 | 现在要求 | 不满足时 |

来源（都是 2026-10-15 当天）：`LAGcomcom/zen-gate#62`、`MingLoong/Aether#71`+`#72`、

**我们做了什么**：`zen-proxy.mjs` 的基址改成 `https://opencode.ai/inference`、去掉两条遗留头、
补 `x-opencode-session-id`、诱饵工具与调用方自带的 `bash`/`read` 都保证"至少一个 property"、
UA 加 `deepseek-harness` → `dsh` 的净化；403 在 App 里**专翻一条**文案
（说清"不是你没配 Key"，并给"换一个自己配了 Key 的模型"这一步）。

**验证与边界（如实写）**：

* `node install/test-zen-proxy.mjs` → 13 项全过（本地假上游；断言钉住了路径常量、
  会话头、两条遗留头必须缺席、工具 schema 必须有 property）。
* ⚠️ **本机（服务器出口）实测仍然 403**：按新契约做了 6 组变体（三种工具集 × 有/无

**⚠️ 结论没变，而且更硬了**：单条通道的"跟着变脸跑"路线**不可持续**（5 次变动，一次比一次快）。
§3 的多源池仍然是正解；在那之前，**别把它设成出厂默认**。

## 2.3 社区调研（2026-10-15 当天做的，用户要求"看看社区有没有好方案"）

### A. 还在追 Zen 免费车道的项目：**最有分量的那个已经放弃**

这一片有 10+ 个 DSH 插件（`x5427876/dsh-opencode-free`、`viztor/dsh-opencode-patch`、
`DragonHorizon-xtihc/dsh-connect-opencode-free`、`defaver04/opencodezen4dsh`、
`garyzakharov/opencode2dsh`、`artorias-zj/dsh-opencode-free-model`、`razureink/0KAY-free-model`、
`yuyang2230/zen-free-lane-bridge`…），今天都还在更新。但其中**测得最扎实的一份
（`viztor/dsh-opencode-patch`）已经明确放弃免费层**，原文要点：

> 把官方客户端的头、CLI User-Agent、形状正确的会话 id、`read`/`bash` 的 tool schema
> **全部带上**，Zen 的 `-free` 模型仍然 `403 FreeTierError`，而**同一个请求换成付费模型就是 200**。
> 甚至用**真实账号的 session token + active org** 测，免费层依然 403。
> 结论：**"门禁不在请求里，是实测出来的"；免费层不是"坏了"，是"没授予"。**
> → 所以这个插件**干脆不提供 Zen 的 `-free` 模型**，只把带 Key 的付费路由做稳。

另一批（`zen-gate#62`、`Aether#71/#72`、`9router-go#322`、`dsh-our-free-model#330`）说
按新契约（路径 `/inference/v1` + 会话头 + 工具 schema + UA）能拿到 200。
**两边对不上**，而我们在本机 6 组变体全 403 —— 最可能的分歧是**出口 IP / 地区**
（有的出口在"被授予"的桶里）。补充一条：`viztor` 还发现网关的
**`/zen/v1`（legacy）与 `/inference/v1`（modern）是分开授权的**，账号在一条上能用不代表另一条能用。

**对我们的结论**：Zen 免费层**不能当产品承诺**；保留成彩蛋、失败如实说、**不设默认**。

## 2.4 实施（2026-10-15 当天就做了）：**Pollinations 免 Key 通道上线**

用户拍板原话：「**主要就是以前承诺过不需要填写 key**」—— 于是当天实施，不是留待讨论：

* 新增 `app/lib/data/polli_channel.dart`：把 `polli` provider（`baseUrl =
  https://text.pollinations.ai/openai`）与匿名层模型写进本机模型配置；
  **不起本地进程**（上游本身就是 OpenAI 兼容的，DSH 自己接 `/chat/completions`、`/models`）。
* `polli` 进 `appProvidedCredentialIds`、`POLLI_API_KEY` 注入占位值 —— 这样界面
  **不会**催用户填 Key（"不用填 Key"必须是事实，不只是文案）。
* `AppSettings.polliEnabled` **默认开**：装完模型列表里就有，不用去设置里找开关。
* Zen 那条降级为「第三方通道」彩蛋（默认关 + 交叉指引 + 失败如实说）。
* 实测（本机，走 App 真正会用的形状）：`/openai/chat/completions` 不带 Key → 200；
  流式、工具调用、`stream_options.include_usage` 全通；连打 5 次不 429。
  局限已写进界面：**匿名层只有一个 20B 级模型**（`openai-fast`）。

⚠️ 仍未做的（§3 那两条）：真正的**多源池**（多上游 + 健康状态 + 故障转移）。
Pollinations 是"一条能用的免 Key 通道"，不是"不会再有这类问题"。

## 2.5 第 6 次变动（2026-10-15 社区摸清）与**我们 2026-10-16 的复测：通了**

**先说结论**：这一次不是"有谁修好了"，而是上游**第 6 次改门禁**、社区当天摸清新形状；
同时**我们这台机器的出口桶也变了**（10-15 本机仍然 403，10-16 变成 200）。
两件事都有实测记录，别把 10-15 的结论当成过时或当成矛盾。

### 新契约（社区两份独立实测互相印证）

| 项目 | 现在要求 | 来源 |
|---|---|---|
| 工具指纹 | **四个**函数工具：`bash` / `glob` / `grep` / `read`（不再是两个） | `Ebony-Vinyl/dsh-our-free-model` 提交 `538b5197`；`artorias-zj/dsh-opencode-free-model` README |
| 工具名 | 门禁按**小写**识别 → 调用方发 `Bash`/`READ` 要规范化成小写再发，回程再把原拼写还回去 | 同上提交 `0525f8a9` |
| 请求 id | `x-opencode-request` 用铸造形状 **`msg_` + 12 位 hex（`ms·0x1000+seq`）+ 14 位 Base62**（原来 `req_` + 哈希） | 同上「同步 OpenCode 请求协议」 |
| 其余不变 | 端点仍是 `/inference/v1/chat/completions`；`x-opencode-session-id` 仍必须；UA 带仍是 `[1.18.0, 1.18.33]` | 同上 |

⚠️ **`viztor/dsh-opencode-patch` 仍然不提供免费层**（它的 README 原话：把指纹全带上，
`-free` 模型仍 `403 FreeTierError`，同一请求换付费模型就 200 → "免费层不是坏了，是没授予"）。
**两边的说法都对**：它面对的是**它那个出口**的桶，我们 10-16 面对的是另一个。
这也是为什么这条通道的定位只能是**彩蛋**，不能当承诺。

### 本机复测（2026-10-16 03:48 UTC 起，走真上游）

| 探测 | 结果 |
|---|---|
| `GET /inference/v1/models` | **200** · 86 个模型 / **10 个免费** |
| `POST …/chat/completions` + 两个工具（旧形状） | **200** |
| `POST …/chat/completions` + 四个工具（新形状） | **200** |
| 经**出货的代理**端到端发一次对话 | **200** + 真内容（`你好呀`） |
| 逐个免费模型打一遍（同一出口、同一时刻） | 6 个 **200**；3 个 `muse-spark-*`/`cat-jam-free` → **403 `RegionError`**；`jev-1.13-free` → **400 `ModelProtocolUnsupported`** |

**两条"形状对≠能用"的教训（都写进代码注释了）**：

1. **`/models` 与 `/chat/completions` 是两道独立的闸**：清单**一律** 200，
   对话才可能 403 → 只看清单的自检会**假通过**（见本节的"通道自检"一段）。
2. **"门禁"与"地区"是两道独立的闸**：同一个请求里，`cat-jam-free` 给 `RegionError`、
   其它给 `FreeTierError`；两者的"下一步"完全不同（换模型 vs 换网络）。

### 我们做了什么

`app/assets/toolbox/zen-proxy.mjs`：四工具指纹（各带至少一个 property）、工具名小写规范化 +
回程还原、`msg_` 铸造请求 id、**真流式**（原来整段收完再吐 —— 函数名叫"流式转发"却不流）、
错误分类补 `RegionError` / `ModelProtocolUnsupported` / `426`、兜底名单换成 2026-10-16 实测的
10 条（`big-pickle` 移出：它在售但**不在免费层**）。

回归测试 `node install/test-zen-proxy.mjs` → **19 项全过**（本地假上游，不碰真上游），
新增断言里最值钱的两条：**首字节 < 200ms**（真流式的判据）、**两种 403 文案必须分开**。

### 通道自检也跟着改了（2026-10-16）

免 Key 那条**不再只看 `/models`**：改走本机代理发一次 `max_tokens: 1` 的对话，
**最多试 3 个**模型（地区封锁是按模型的），第一个 200 就算通；403 拆成
"门禁（blocked）"与"地区（region）"两种结论、给不同的下一步。
——这一条是被 §2.5 那张"两道闸"的表推出来的：**假通过比不报还坏**。

### 3.2 机制（复用 App 里**已有**的「轮换池」基础设施）

1. 每个源一份**健康状态**：最近成功/失败时间、上次失败原因、今日用量；
2. 失败（429 / 5xx / 403 / 超时）**自动换下一个**（现有粘性 lastGood 逻辑照搬）；
3. 启动时**可选**做一次极轻的探测（每源 1 次，不循环、不重试轰炸）；
4. 界面**如实显示**每个源的状态与余额，并说明为什么跳过它（绝不假装成功）；
5. 全部源不可用时**明确报错 + 给下一步**（这一条现在就已经做对了）。

### 3.3 模型清单（目录）怎么更新

就是 FreeLLMAPI 那条「签名 feed」的轻量版。

## 5. 需要用户拍板

1. 至少注册一个免费源（**推荐智谱**，5 分钟、永久免费）；或明确「只用 OVH 那个免注册的」
   （2 次/分钟，只够试玩）。
2. 先做 B、还是 B+A 一起。
### 5.1 为什么不做 IP 池（多出口轮换）

1. **手机端没有这个基础设施**：代理跑在**用户手机**里，而"IP 池"意味着流量要经过**一批代理出口** ——
   要把这条路做出来，得**用户自己买/搭代理**并配到手机上（普通用户做不到）；
   没有真实出口的"IP 池"就是个摆设。
2. **它对付不了今天这类问题**：今天挂掉的原因是**按客户端识别（403 FreeTierError）**与
   **地区封锁（403 RegionError）**，而不是"按 IP 的配额" —— IP 池只分担后者。
   也就是说：**当初就算做了，今天照样死**。
3. **风险落在用户自己的出口**：按 IP 的封禁封的是**用户家/手机的出口**，不是我们的。
4. 所以这里的选择是：**换源**（一家不行换一家，而且是各家的**公开免费额度**），
   而不是**伪装 + 多出口规避**同一个源。

3. **产品口径**：把卖点从「**不用填 Key**」改成「**注册一次、永久免费**」——
   这才是能长期兑现的承诺（今天的坏消息正好证明「零 Key」不可持续）。
