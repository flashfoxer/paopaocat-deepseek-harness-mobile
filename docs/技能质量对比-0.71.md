# 技能质量横向对比（自家 37 技能创作包 vs 内置 14 个）

> 依据：用户 2026-10-12 在台账 #80 里排的第 ③ 项 ——
> 「拿自家那套 **37 技能创作包**做参照，挑出能替换/增强内置技能的，并写清**为什么质量更高**
> （不许只喊口号）」。
>
> 参照物：`dsh-agnes-studio` 插件里随包的那套（磁盘位置
> `/dsh/profiles/web/node_modules/dsh-agnes-studio/**/skills/*/SKILL.md`，共 **37 个** SKILL.md）。
> 被评对象：本 App `assets/skills/` 下的 **14 个**内置技能。
>
> 本文**只读对比、不动代码**。结论都附可核查的数字或原文结构。

---

## 0. 一句话结论

**一个都"换"不了**（两边是**不同领域**：他们是小说/短剧/视频解说/小说改游戏，
我们是办公与日常）；但**有 4 处方法可以直接吸收**，外加 **1 处结构级改进** —— 下面第 3、4 节。

## 1. 硬数字（可核查）

| 指标 | 自家创作包（37 个） | 我们内置（14 个） |
|---|---|---|
| 正文合计 | **264,642 字符** | 35,453 字符 |
| 平均每技能 | **7,152 字符** | 2,532 字符（**0.35×**） |
| 最短 / 最长 | 1,535 / 45,075 | 1,736 / 3,795 |
| 二级标题（`##`） | 295（8.0/技能） | 95（6.8/技能） |
| 三级标题（`###`） | **166（4.5/技能）** | **1（0.1/技能）** |
| 显式阶段标记（`Phase N` / `### S N` / `步骤 N`） | **190 处** | **0 处** |
| 随技能的按需加载文件（`references/*.md`） | **254 个** | **0 个**（只有 SKILL.md） |

**怎么读这张表**（别读成"他们的更好"）：

* 差得最多的是**结构**，不是长度：他们每个技能有 4.5 个三级标题、**190 处显式阶段**
  （`Phase 1…5`、`S0…S5`），我们**一处都没有** —— 我们的技能是**紧凑操作卡**（先问什么 →
  怎么调工具 → 失败怎么说人话），他们是**可导航的手册**（阶段 → 每阶段产物 → 交接）。
* 第二是**渐进式披露**：他们有 **254 个 `references/*.md`**，主文件只留索引与触发条件；
  我们**单文件、零附件**。同样的"每轮固定开销"预算下，他们能装进多得多的深度。
  （我们 0.29 那次把 12 条技能**简介**从 927 压到 242 字符，目标一样，但只做到了简介层。）
* 我们**强在他们没有的那一条**：**本机环境绑定** —— 正文里全是能真跑的东西
  （`node -e` 一行读文件、`$DSH_ANDROID_TOOLBOX` 脚本、手机没有 python、长任务要等、
  失败必须说人话）。他们假设的是**电脑 + 浏览器 + Python + vendor 脚本**，
  直接搬到手机上，正文里大半是死路。

## 3. 四处可直接吸收的方法（P1/P2，只改 SKILL.md 正文）

> 判据：**方法可搬、依赖不可搬**。下面每条都写清"他们有什么、我们缺什么"。

### ① `make-video` ← `short-drama-video-prompts` 的**维度清单**（P1）

* 他们那份（15,825 字节）的正文结构是：`入口与边界 → 工作流 → **提示词要求** → 按需知识 →
  完成与投产`；简介里点明要覆盖：**文生/图生视频的动作、人物表演、运镜、口型、环境运动、
  镜头时长、起止状态**。
* 我们的 `make-video`（1,871 字符）讲的是：**怎么调工具箱、参数怎么填、失败怎么读**。
* **缺的那一块**：没有任何"把视频提示词写对"的清单。用户要"让人物走起来"时，
  我们只告诉他调哪个脚本，却没告诉他提示词里必须交代哪几件事（动作幅度、镜头运动、
  时长、首尾状态）—— 这直接决定生成质量。
* **做法**：把"八维度"重写成一段中文清单（适配我们自己的 `make-video.mjs` 参数），
  **不要**照抄他们的分镜/冻结关键帧术语（那是短剧项目才有的东西）。

### ② `make-image` ← `short-drama-image-prompts` + `short-drama-assets` 的**一致性锚点**（P1）

* 他们的定位是：角色设定图、**三视图**、参考图、场景板、道具图、风格帧、
  Look Development、**状态变体**，以及"判断复用还是新变体""**跨场连续性**"。
* 我们的 `make-image` 只讲：生成、按参考图改图、多图合成 + 调用参数。
* **缺的那一块**：**同一个角色/同一个场景在多张图里保持一致**的方法
  （锚点图怎么定、什么该复用、什么必须新变体、状态怎么标）。这是"多图合成"之外、
  用户真正会踩的坑（生成 5 张图，人物长得都不一样）。
* **做法**：给 `make-image` 加一节「一致性锚点」，用我们自己的 `--ref` 参数落地。

### ③ `translate-polish` ← `story-deslop` 的**去 AI 味**（P1）

* 他们那份（21,429 字节）有：**核心哲学 4 条**（改味优先不当改错 / 改最少效果最大 /
  保留创作意图 / 有功能的语气停顿要留）+ **自然文本基准**（自然特征与 AI 味对照表 +
  自然表达替换参考）+ **检测流程 Phase 1–5**（扫描 → 诊断分级 → 逐项清除 → 确定性收尾 →
  输出润色）+ 固定的**检测报告与"改前改后"输出格式**。
* 我们的 `translate-polish`（2,014 字符）是"互译 / 润色 / 本地化"。
* **缺的那一块**：**"去 AI 味"这件事本身**。用户拿一段 AI 写的周报/文案说"太假了"，
  我们现在只能泛泛润色，没有判定标准和检测流程。
* **做法**：加一节「去 AI 味」，借它的**哲学与流程骨架**，但**语料必须换成中文办公文体**
  （它的替换参考是网文腔，照搬会变成"把周报改成小说腔"）。

### ④ `doc-digest` / `doc-processing` ← `short-drama-novel-analyze` 的**拆解管道**（P2）

* 他们那份（14,855 字节）是显式管道：`S0 章节索引 → S1 改编价值快评 → S2 逐章功能提取 →
  S3 剧情单元与节奏 → S4 人物与设定 → S5 改编价值与分集候选 → 交接`，
  另有「规则分级」「产物与边界」「语言」「按需加载」。
* 我们的 `doc-digest`（2,195 字符）是"要点 / 时间线 / 速读稿"。
* **缺的那一块**：**可复查的分阶段产物**。长材料（一份 50 页报告、几十轮对话导出）
  只看摘要无法核对；他们的做法是每阶段都落一个文件、最后有交接契约。
* **做法**：给 `doc-digest` 加"分阶段 + 每阶段落盘 + 交接"的骨架（阶段名换成办公语境：
  目录索引 → 结构与功能 → 单元聚合 → 人物/术语/数据归并 → 结论与待办）。

## 4. 一处结构级改进（P3，需改代码）：学他们的**渐进式披露**

他们有 **254 个 `references/*.md`**：SKILL.md 只留**索引 + 触发条件 + 边界**，
细节按需加载。我们 **0 个** —— 单文件、深度受每轮开销限制。

⚠️ **但这正好和另一件事是同一个前置**：如果要引入 `diagram-design`（台账里"值得做、
但要先改安装器"那条），它也是**多文件技能**（SKILL.md + references/ + assets/，4.89 MB），
而现在 `BuiltinSkills.install` **只写一个 SKILL.md**。

**所以：一次把 `BuiltinSkills.install` 改成"整目录安装"，两条需求同时解锁。**
这是把它排在 P3 而不是更后的原因 —— 它是**前置改造**，不是一次性收益。

## 5. 我们的空白：他们有一条"视频解说"流水线

他们的 6 个视频解说技能构成一条闭环：
`video-understanding`（场景检测 / ASR / 逐场景 VLM 观察 / 融合时间线）→
`video-script`（导演与剪辑策划 + 带时间戳解说）→ `video-cut`（按区间剪）→
`video-voiceover`（TTS 逐段合成）→ `video-assemble`（铺旁白 / 压原声 / 字幕 / 响度）。

**我们能拼出其中三段**（已有 ffmpeg + 三家 TTS：系统 / MiMo / MiniMax，
以及本次刚做的本机播放/合成链路），**缺的是"理解"（ASR + 逐场景观察）与整套编排**。
这可以作为一条独立产品线立项（不是技能搬运，是功能开发）。

## 6. 明确**不**搬的（附理由）

| 对象 | 为什么不搬 |
|---|---|
| 网文 13 个（`story-long/short-*`、`story-setup`、`story-cover`、`story-import` 等） | **领域不同**：它们是"写小说/拆网文/扫榜/封面"，我们的定位是办公与日常。只有 `story-deslop` 的**方法**值得借（见 3-③） |
| `browser-cdp` | 手机上**没有 Chrome / CDP**；这套东西在本机跑不起来（我们早在 0.47 就因同类原因收敛过端侧玩法） |
| `story-review`（多视角对抗审查） | 它 spawn 并行 reviewer agents 并读参考文件；**手机端没有那套 agent 基础设施**。方法是好的，但落地要重写成"交付前自查清单"（另行立项） |
| 其余的短剧/小说改游戏技能 | 正文普遍依赖**项目目录结构 + vendor 脚本 + 参考文件 + reviewer agents**；直接搬过来，正文里大半是死路（而且我们 **0 个** references 目录，连放的地方都没有 —— 见第 4 节） |

| 优先级 | 做什么 | 动什么 | 代价 |

| **P2** | `doc-digest` 加「分阶段拆解 + 交接」 | 只改该 SKILL.md | 中 |
| **P3** | 安装器改「整目录安装」（同时服务 `diagram-design`） | `lib/data/builtin_skills.dart` + `pubspec.yaml` | 中（架构改动，需测试） |
| **立项（非技能）** | 「视频解说」整条流水线（理解 → 解说 → 剪辑 → 配音 → 合成） | 新工具箱脚本 + 影视页入口 | 大 |

**注意两件事**：

1. P1/P2 都是**只动技能正文**（`assets/skills/*/SKILL.md`，属 asset）、**不碰 Dart 代码** ——
   但它们改了**随包内容**，所以**仍然要出新包才能到用户手里**。
   `install/check-release.py` 是拿 `dist/` 里最新的 APK 与当前源码树比对，
   所以它会先 FAIL 直到出新包 —— 那是**预期**的，不是代码错。
2. 版本号仍留在 **0.71**（按台账的版本规矩：**产物给过用户一次才 +1**，而 0.71 至今没给过用户）。
   P3（安装器改造）才算"要升版"的那类改动；不过既然 0.71 还没交付，它也可以并进 0.71。
