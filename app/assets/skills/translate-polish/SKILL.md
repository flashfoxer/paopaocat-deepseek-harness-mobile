# 中英互译与润色

本技能负责：把一段原文翻译并润色成目标语言，产出**双语对照**文件；也负责只润色不改语言。
什么时候用：用户说「翻译成英文 / 翻成中文 / 润色一下 / 帮我改得更地道 / 做成双语对照」。

产物：`双语-<原名>.md`（原文与译文逐段对照），需要时再来一份自包含 `双语.html`。

## 0. 先确认（一次问完）
- 原文在哪（工作区文件路径或直接粘贴）？**源语言和目标语言**分别是什么？
- 用途与语气：正式文档 / 邮件 / 产品文案 / 学术 / 口语；读者是谁。
- 专有名词：人名、品牌、产品名、术语要不要保留原文？有没有已有的固定译法？
- 只要译文，还是双语对照，还是同时要「润色版」？

源语言不确定时先判断并告诉用户你的判断，再动手。

## 1. 读原文
```sh
node -e "const t=require('node:fs').readFileSync('原文.md','utf8');console.log('字符数',t.length);console.log(t.slice(0,3000))"
```
- 保留原文的**结构**：标题层级、列表、表格、代码块、链接、加粗，一一对应到译文里。
- 代码块、变量名、文件路径、URL、命令**不翻译**，原样保留。
- 长文分段处理，逐段译，保证术语一致；文件超过几万字符就分批读写（见第 3 节）。

## 2. 建术语表（超过 500 字就该建）
在 `双语-<原名>.md` 顶部先写一张小表：

| 原文 | 译法 | 说明 |
|---|---|---|
| DSH | DSH | 产品名不译 |
| skill | 技能 | 与产品内文案一致 |

术语一旦定下，全文统一；中途改口径就回头把前面改掉。

## 3. 翻译与润色要求
- 译文要像目标语言**母语者**写的，不是逐词对译：拆长句、补主语、调整语序、按目标语言习惯用标点。
- 中文里不要出现英文式被动与「的的的」长定语；英文里不要出现中式流水句。
- 语气统一：不要一段正式、一段口语。
- 润色模式（不换语言）要写清改了什么，按「原句 → 改后 → 为什么」列在文件末尾的「改动说明」里。
- **不加**原文没有的事实、数据、承诺；拿不准的地方在文件里用「【待确认：…】」标出，并在回复里说明。

逐段对照的写法：
```
> 原文：Original paragraph goes here.
> 译文：这里是译文段落。
```
长文也可以按段落编号 `[1] [2]` 对照，方便用户核对。

## 3.1 去 AI 味（用户说「太假了 / 一看就是 AI 写的 / 帮我改得像人写的」时走这一节）

润色与**去 AI 味**是两件事：润色是把话说得更好，去 AI 味是**把"机器腔"消掉**。
四条原则（照这个顺序想）：

1. **改味优先，别当改错**。AI 味的句子通常语法没错、信息也没错，只是"不像人说的"。
   所以别去纠正它，而是要**换成一个人真的会怎么说**。
2. **改最少，效果最大**。一段话改掉两三处最刺眼的就够了。整篇重写会让原文的语气与立场一起没了 ——
   那比 AI 味更糟（用户会觉得"这不是我写的了"）。
3. **保留创作意图**。作者想强调的、想留白的地方不要动；不要为了"自然"把有力的短句改成温吞的长句。
4. **有功能的语气与停顿要留**。"总之"、"其实"、"你猜怎么着"这类词如果是作者的语感，就别删；
   只有当它是**空转的口头禅**时才删。

**中文办公文体里最常见的 AI 味（逐个对照）**：

| AI 味长这样 | 为什么假 | 改成 |
|---|---|---|
| 「首先…其次…最后…」三段式 | 结构先于内容，什么都用同一套骨架 | 按事情本身的顺序说，不必凑三段 |
| 「赋能 / 闭环 / 抓手 / 对齐 / 颗粒度」 | 万能名词，说了等于没说 | 换成具体动作（"把 A 和 B 合到一个流程里"） |
| 每句都"不仅…而且…" | 对仗成瘾，读起来像稿子 | 拆成两句大白话 |
| 每段长度几乎一样 | 人写东西不会这么齐 | 该短的短（一句话一段也正常） |
| 「值得注意的是 / 综上所述 / 由此可见」 | 空转的连接词 | 直接说结论，或干脆不写 |
| 形容词堆叠（"深刻而重要且具有深远意义"） | 只在抒情，不给信息 | 说清"对谁、有什么用" |
| 「让我们一同…」式动员 | 假热情 | 说清要做什么、什么时候 |
| 破折号里塞同义重复 | 两个说法其实一个意思 | 留一个 |
| emoji 与感叹号滥用（🚀 太棒了！） | 语气不真 | 除非原文就这风格，否则去掉 |

**检测流程（四步，别跳）**：
1. **扫描**：通读一遍，把"读着别扭"的地方标出来（不急着改）。
2. **分级**：分成「必须改」（一眼假、与事实不符的语气）/「可选」（改了更自然）/「不动」（作者风格）。
3. **逐项清除**：只改前两级，每处都问自己"一个真人会这么说吗"。
4. **收尾自查**：事实、数据、结论**一个都没变**；原意没被削；专业术语没被口语化简写成别的东西。

**输出格式**（放在产物文件末尾的「改动说明」里）：

```
## 改动说明（去 AI 味）
1. 「首先…其次…最后」→ 按时间顺序直述
2. 删掉「赋能/闭环」等 6 处万能名词，换成具体动作
3. 合并 3 组同义重复的破折号
（共改 11 处，事实与数据未动）
```

**边界（必须守住）**：
- **只改读感，不改事实**：数字、日期、结论、承诺一律不动。发现原文里这些有问题，**另行标出**（`【待确认：…】`），
  不要顺手"改顺"。
- 用户要的是"更正式/更书面"时，**不要**硬去 AI 味 —— 那种场合的对仗与套话可能正是他要的（官方函件、公文）。
  先问一句，或者只在明显不通顺处动。
- 网文/小说/文案的语气规则不一样（例如短句、口语、网络用语是**风格**不是 AI 味），
  拿不准就按上面 4 条原则逐句问"这句是机器腔，还是作者的声音"。

## 4. 分块处理长文（避免一次读爆）
```sh
node -e "const t=require('node:fs').readFileSync('原文.md','utf8');const parts=t.split(/\n(?=#{1,3} )/);parts.forEach((p,i)=>require('node:fs').writeFileSync('段'+i+'.md',p));console.log('切成',parts.length,'块')"
```
译完再用 node 合并回 `双语-<原名>.md`（不要用 `cat` 拼中文文件，容易出编码与顺序问题）。

## 5. 自检与交付
```sh
node -e "const f=require('node:fs');const a=f.readFileSync('原文.md','utf8'),b=f.readFileSync('双语-原文.md','utf8');const cnt=(s,m)=>(s.match(m)||[]).length;console.log('原文标题',cnt(a,/^#{1,3} /gm),'译文标题',cnt(b,/^#{1,3} /gm),'文件字节',b.length)"
```
- 标题、列表、代码块数量应与原文一致；差得多说明漏译了，回去补。
- 回复里给：产物**路径原样**、术语表、你标出的「待确认」条目。

## 诚实约束
- 读不到文件就贴**真实报错**，让用户把原文粘贴过来。
- 这台设备上没有 python / pandoc / 词典 API，也**没有可靠的联网翻译服务**：
  翻译能力就是你自己，不要试图调外部接口，也不要假装查过词典。
- 不要编造原文里没有的事实；专业领域（法律、医学、合同）要提醒用户「建议人工复核关键条款」。
- 用户要 `.docx` 成品时**能做了**：`node "$DSH_ANDROID_TOOLBOX/make-docx.mjs" 双语-原文.md 双语.docx`
（Markdown 子集：标题/段落/列表/引用/代码块/表格；列表是文字前缀、不支持图片与目录）。
`.pdf` 仍然做不到，如实说 —— 可给 `.docx` 或离线 HTML。
