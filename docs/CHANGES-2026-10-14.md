# DSH 手机版「会话丢失」修复单

**交办对象**：负责 DSH 手机版客户端（包名 `com.dshmobile.dsh_mobile`）及其 ACP 会话层的开发方
**被测版本**：v0.74（versionName 0.0.74，versionCode 74，release）
**机型/系统**：nubia NX809J（REDMAGIC，QTI SM8850）/ Android 16（SDK 36）/ arm64-v8a
**用户现象一句话**：点开历史会话，里面是空的，以为对话被删了。
**核查结论一句话**：磁盘上没有任何会话被删除或损坏；"空"是 App 自己造出来的。**要修的是下面 4 处，另有 1 处环境问题。**

---

## 0. 结论速览

| 编号 | 缺陷 | 优先级 | 用户可见后果 |
|---|---|---|---|
| A | 零消息空壳会话被写入磁盘并进入会话列表 | 高 | 列表里一批"没标题、点开全空"的会话，把真实对话淹掉 |
| B | 切模型时日志称"会话未重建"，实际新建了会话，旧会话被弃 | 高 | 正在进行的对话"跳"到另一个会话，上一条提问失联 |
| C | 提问失败的原因不写入会话转录 | 中 | 回看时只有自己发的话、没有回答、也没有任何报错说明 |
| D | 同一会话并发 prompt，触发 `a prompt is already in flight` | 中 | 连点发送会白丢一轮 |

环境问题：`zen/*` 免费通道已基本不可用（403/410/429），见 §6。不是客户端代码缺陷，但需要同步处理。

## 1. 数据结构（先看这节，省得找错地方）

- **会话目录**
  `/data/user/0/com.dshmobile.dsh_mobile/files/dshhome/sessions/--data-user-0-com.dshmobile.dsh_mobile-files-workspace--/<sessionId>/`
  （外层目录名是 cwd 的转义：路径里的 `/` 变成 `-`）
- **转录文件**：`session.v4.jsonl.zstd`
  **多帧 zstd 拼接**，每帧内是若干行 JSONL。出现的事件类型：
  `session` / `session/title` / `user/message` / `assistant/message` / `assistant/attempt` / `llm/retry` / `llm/retry-started` / `turn/start` / `turn/end` / `step/start` / `step/end` / `tool/call` / `tool/result` / `session/end-seed` / `permission/preset` / `sandbox/mode` / `approval/policy` / `agent/inbox/spliced` / `request/context` / `request/header` / `system/message`
- **投影缓存**：`…/dshhome/storages/session_projcache/sessions/<sessionId>.json`
  判断会话是否真聊过，看 `record.rows.titleInput.val.count`、`record.rows.turnBoundary.val.lastTurn`、`record.rows.tokenUsage.val.totals` 三个字段即可。
- **回放读取器**：`/data/user/0/com.dshmobile.dsh_mobile/files/tools/read-transcript.mjs`
  （**改转录格式必须同步改它**，否则回放全空）
- **诊断日志**：`…/files/logs/dsh-diagnostic.log`（当前）、`dsh-diagnostic.log.1`（上一份）
- 附注：`…/files/workspaces.json` 里的 `sessionTitles` 是空对象 `{}`，没被用上 —— 会话标题只存在转录和投影缓存里。

## 2. 缺陷 A：零消息空壳会话写入磁盘并进入列表

### A.1 数据

48 个会话目录中，**17 个从头到尾只有头部记录：0 条消息、0 token、无标题**；其余 31 个有真实内容。

**关键反证**：全部 48 个会话里，**"有 token 消耗但转录为空"的会话 = 0 个**。也就是说，聊过天的会话一条都没被掏空。

### A.2 三条产生路径（都有日志时间线）

**A-1　打开聊天页即建会话**

```
22:50:24.107 [dsh-nav]        open chat page (initialText=- resume=- cwd=…/workspace)
22:50:25.694 [print:chat]     [acp] session created: 047208a4-2d28-43e4-904e-1970f59583b6
22:50:28.444 [print:dsh-live] detach /data/user/0（进程保留，回答继续）   ← 一句没发就走了
```

全域统计：**22 次 `open chat page (resume=-)`，只有 10 次在 120 秒内真的发出了 prompt** → 12 次白建。

**A-2　首页「内置会话」入口**

```
16:49:19.181 [print:dsh-home] 内置会话 -> make-video（生成一段视频）
16:49:19.182 [print:dsh-nav]  open chat page (initialText=用 make-video 技能帮我生成一段视频。… resume=- …)
16:49:21.198 [print:chat]     [acp] session created: 74a86dab-c59d-4e72-9104-176193428163
（其后 3 秒内用户 swipe 去了别的 Tab；initialText 从未发出，全程没有 prompt 行）
```

这类会话额外留下 `session/end-seed` 标记。全期该入口被用了 4 次，对应会话全是空壳。

**A-3　切模型另开会话** —— 与缺陷 B 同源，见 §3。

### A.3 期望行为（建议）

1. 打开聊天页**不要**先落盘会话；等用户发出第一条 prompt 再创建。必须预创建时放内存，未使用则丢弃。
2. 会话列表过滤 0 消息会话。判据二选一：
   `projcache.record.rows.titleInput.val.count === 0 && projcache.record.rows.turnBoundary.val.lastTurn === 0`，
   或直接看转录里有没有 `user/message`。
3. 给存量空壳一个清理入口（或在升级时一次性清理）。

### A.4 验收标准

- 只点开聊天页、不发消息 → 磁盘不新增会话目录。
- 点首页「内置会话」但不发送 → 磁盘不新增会话目录。
- 列表条数 == "至少含一条 `user/message` 的会话数"。

## 3. 缺陷 B：切模型谎报"会话未重建"

### B.1 证据（同一秒内自相矛盾）

```
23:06:42.064 [print:chat] 会话内切换模型成功：com/deepseek/deepseek-v4.1-flash（会话未重建，已由运行时确认）
23:06:42.185 [print:chat] [acp] process exited with 0
23:06:43.717 [print:chat] [acp] session created: 348524f2-8d8e-463a-bac0-a0995d3f04cb
```

用户在旧会话 `c6a74bd7` 里刚发过 prompt（23:05:56），切完模型界面到了新会话 `348524f2`，旧会话被留在列表里当空壳。

同类至少还有 3 处：`ad039bbd→92168182`（13:17）、`f9212a49→8579d495`（14:49）。

### B.2 反例（说明行为不一致，不是"总是新建"）

`74a86dab` 切到 agnes 时是**真的续用同一个 ID**：

```
16:49:45.115 [print:chat] model changed -> agnes-3.0-flash
16:49:46.650 [print:chat] [acp] session resumed: 74a86dab-c59d-4e72-9104-176193428163 model=agnes/agnes-3.0-flash
```

据现有证据推断的规律（**需以代码为准**）：干净会话切模型 → resume 同一 ID；存在失败/未完成轮的会话切模型 → 新建会话。若确实如此，等于"上一次失败连带把整个会话顶掉了"。

### B.3 期望行为（建议）

- 二选一，别含糊：
  - 切模型**必须**续用同一会话、把上下文带过去；或
  - 明确"开局新会话"，但要把旧会话最后状态、以及"上下文已断开"写进新会话并提示用户。
- 无论选哪条，`会话未重建` 这句文案必须与实际行为一致。

### B.4 验收标准

- 切模型前后，界面显示的 sessionId 与磁盘新增目录能对上账；日志文案与实际一致。
- 在"刚发过 prompt 且该 prompt 失败"的会话里切模型，旧会话不会变成 0 消息空壳。

## 4. 缺陷 C：提问失败的原因不写进会话

活标本是 `c6a74bd7`。用 App 自带读取器回放：

```
$ node tools/read-transcript.mjs dshhome c6a74bd7-0ca8-46fa-9fbd-a8dd3a30e216
{"title":"请阅读这个文件：/data/…","createdAt":1791990352081,"total":5,"capped":0,
 "messages":[{"role":"user",…} ×5]}          ← 5 条全是 user（1 条真实提问 + 4 条系统注入）
                                               assistant/message = 0，且没有任何错误事件
```

同一时刻诊断日志里原因其实很明确：

```
23:06:13.897 [print:chat] prompt failed（第 1 次）: … Connection error.
23:06:30.117 [print:chat] prompt failed（第 2 次）: … Connection error.
```

同类会话共 6 个（`c6a74bd7`、`42fa256a`、`060dabe1`、`b9206adb`、`14bc2f2e`、`fd5af40c`），特征一致：有 `assistant/attempt` 与 `llm/retry*`，`assistant/message` 为 0。

> **一处澄清，请勿按此改**：诊断报告**没有**隐瞒这类失败 —— `prompt failed` 是以 `E` 级记录的（10-10 那份报告里就是 `[E×3] print:chat | prompt failed（第 # 次）…`）。用户手上这份报告写"没有错误或警告"，只是因为它生成于 23:05:34，而失败发生在 23:06:13 之后。要改的是"失败不进会话"，不是报告统计。

### 期望行为（建议）

失败时向转录写入一条可回放事件（如 `turn/error`，含 code / 原因 / 是否可重试），UI 上显示"上一条没有回答，原因：…"，并给重试入口。

### 验收标准

- 断开上游后发一条消息 → 会话文件里能看到失败事件，而不只是 `assistant/attempt`。
- 重开该会话回放，能看到失败提示。

## 5. 缺陷 D：同一会话并发 prompt

日志里 4 次直接失败：

```
16:55:56.050 prompt failed（第 2 次）: … Invalid params: a prompt is already in flight for this session
16:56:07.745 / 16:56:08.350 / 17:04:28.010  同样报错
```

说明客户端在上一条 prompt 还没结束时又发了一条。注意其中 2 次紧跟 `TimeoutException: ACP 请求超时：session/prompt` —— **超时路径没有收尾就又发了下一条**。

建议：in-flight 期间禁用发送按钮（或把输入排队）；超时后补 `session/cancel` 并复位状态，别让会话卡在"有 prompt 在飞"的状态里。

## 9. 修复优先级建议

1. **A + B 一起做**：它们是同一条链路（会话创建/重建时机），一起改才能保证"列表里每一条都点得开、点开都有内容"。
2. **C 次之**：失败可见性，能立刻消掉"我的会话丢了"这类误报。
3. **D 再次**：并发与超时收尾，属稳定性。
4. 环境问题（§6）可并行：先把默认路由换掉，能立刻减少上面四类里一半的触发量。

## B.1　缺陷 A：0 消息空壳

| 改在哪 | 改法 |
|---|---|
| `app/lib/ui/pages/chat_page.dart` `_start()` | **删掉** `else { sessionId = await acp.newSession(ws); }`，改成 `sessionId = null` + 一句日志："进程就绪；会话延后到第一条消息再创建" |
| `chat_page.dart` 新增 `_ensureSession()` / `_createSession()` | 第一条消息到达时才 `acp.newSession(_cwd)`；并发只允许一次（多次调用共享同一个 Future） |
| `chat_page.dart` `_send()` | 开头改成：`_sessionId == null` 就先 `await _ensureSession()`；建不出来**如实报错**（红色气泡 + 原始原因），不把消息吞掉。加 `_sendBusy` 防连点 |
| `app/lib/local/session_projcache.dart`（**新文件**） | 判"是不是空壳"：投影缓存（明文 JSON，Dart 能读）**+** 转录文件大小（多帧 zstd 解不了，但 stat 得到）两路互证 |
| `app/lib/local/session_index.dart` | `session/list` 拿到的每一行都标一个 `emptyShell`（**只标不删**），日志写出"其中 N 条是 0 消息空壳" |
| `app/lib/data/workspace_store.dart` | `DshSession` 加 `emptyShell`；`sessionsOf()` 跳过空壳；新增 `hiddenEmptySessions` |
| `app/lib/ui/pages/workspace_page.dart` | 那行小字改成"磁盘历史会话 {0} 条（其中 {1} 条是空会话，没列出来）"——**数字对不上会被当成还在丢** |

**判据为什么用两路互证**：判错的代价不对称 —— 把真聊过的会话藏起来 = 用户真的丢东西，
多列一条空壳只是难看。所以：缓存说空、**且**转录 < 4 KB 才判空；任何一路读不到 → `unknown` → 照常显示。
4 KB 的依据：设备上 17 条空壳的转录是 **175 B ～ 410 B**，真会话是 KB 级起步。

**验证**：`app/test/session_shell_filter_test.dart`（10 条）钉住全部判据，含
"缓存说空但转录很大 → 判有内容"、"没有缓存 → unknown"、"坏 JSON → unknown"、
"少一路佐证 → unknown"，以及界面侧"空壳不列、但总数与差值都要如实报出"。

**没做的（要你定）**：存量空壳的**一次性清理**没做 —— 删用户目录是不可逆动作，
不该由一次升级自动执行。它们只是不再列出来；要清就手动删
`<filesDir>/dshhome/sessions/*/<sessionId>/`（判据见 8.C 的命令）。

## B.2　缺陷 B：切模型"偷偷换会话"

| 改在哪 | 改法 |
|---|---|
| `chat_page.dart` `_createSession()` | 拿到新 sessionId 后 **`_resumeId = id`**（并同步 `_live.sessionId`）—— 这是根因：`_start()` 判断"恢复还是新建"**只看 `_resumeId`**，而它以前只在 `initState` 从 `widget.resumeSessionId` 取一次，本页新建的会话永远是 null |
| `chat_page.dart` `_applyModelChangeOnce()` | 第三种理由：`_sessionId == null` 时说"还没开始对话，正在按新模型准备会话…"，不再说"正在重建会话" |
| `chat_page.dart` `_restartSession()` | 作废重建中的 `_sessionCreation`（它的 id 属于旧进程） |

改完的效果：**任何**重建（切模型 / 配置变化 / 补一次重建）都走 `session/resume` 恢复同一个会话，
不再产生第二个 id、也不再出现"提示说没重建、实际新建了"。

**验证**：全量测试通过（含既有的 `session_registry_test`）；
`_resumeId` 的写回点只有两处：`initState`（来自 `widget.resumeSessionId`）与 `_createSession()`（新建成功时）；读它的只有 `_start()`、`findReusable` 与 LiveSession 的 key。
**真机待验**：切模型后 `[acp] session resumed: <同一个 id>`，磁盘上不新增会话目录。

## B.3　缺陷 C：失败不进会话

| 改在哪 | 改法 |
|---|---|
| `app/lib/local/session_failure_store.dart`（**新文件**） | `<filesDir>/session_failures.json`：sessionId → 最近一次失败的「时刻 + 人话原因 + 技术细节」。先写 `.tmp` 再改名（被杀不会留半截 JSON）；**上限 50 条**、同一会话只留最新 |
| `chat_page.dart` `_send()` | 两次都失败 → `recordSessionFailure(...)`；**成功一次** → `clearSessionFailure(...)`（擦掉，免得回放挂着过期的"没回答"） |
| `app/lib/local/session_transcript.dart` | 新增 `notice` 角色 + 纯函数 `mergeFailureNotice()`：回放时若**最后一条是用户消息**（说明这轮真没回答）且失败发生在会话创建之后，就在末尾挂一条 |
| `chat_page.dart` `_historyBlock()` | `notice` 画成**红色「没有回答」+ 原因 + 原始报错**，不画成助手回答 |

**如实说明（写进代码注释和给用户的说明里）**：这**不是** DSH 转录里的事件 ——
转录由运行时写，它只在失败时落 `assistant/attempt` + `llm/retry*`，不落错误事件。
要让"会话文件本身就有失败事件"，得改 dsh-acp 的落盘（上游）。

**验证**：`app/test/session_failure_store_test.dart`（9 条）钉住
"同一会话只留最新一条"、"成功就擦掉"、"上限 50 丢最旧"、
"最后一条是助手消息 → 不合并"、"失败早于会话创建 → 不合并"。
